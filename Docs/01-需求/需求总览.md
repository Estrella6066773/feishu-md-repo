# 需求总览

- 状态：待校验
- 最后更新：2026-08-01

## 问题背景

团队文档常同时存在两套入口：

- **Git**：版本清晰、可审查、适合 Markdown / 仓库型文档；
- **飞书**：阅读与协作方便，但与仓库内容容易脱节。

两套入口各自为政时，会反复出现「仓库改了、知识库还是旧的」这类问题。

## 目标

在本机构建一个本地应用，把两者接起来：**以 Git 中的跟踪文件为准**，按绑定规则推送到飞书知识库或云空间；必要时把飞书上的评论拉回仓库，并可用机器人在群里触发同步或接收结果播报。

## 目标用户与场景

| 场景 | 说明 |
|------|------|
| 设计 / 程序文档写在 Git，希望知识库里始终有一份可读镜像 | 工作区模式或仓库模式同步 |
| 有云仓库（如 GitHub）定时拉取后更新飞书 | 有云库 + 定时触发 |
| 本地库提交后自动同步 | `post-commit` hook |
| 在飞书里看到 Mermaid 流程图、CSV/表格、文档总览思维导图 | 正文转换与画板能力 |
| 群里用指令同步，并把成功 / 失败与 commit 详情播报到指定群或用户 | 机器人协作 |

## 设计原则

| 原则 | 含义 |
|------|------|
| Git 为准 | 只同步 Git 已跟踪路径；不扫未跟踪工作区文件 |
| 本地优先 | 核心服务默认只监听 `127.0.0.1`；密钥不进仓库 |
| 映射复用 | Git 路径与飞书节点 token 持久对应，避免每次重建 |
| 可观测 | 同步分阶段进度、日志、队列状态、机器人连接状态 |
| 可中断 | 同绑定上新的手动任务可抢占进行中的旧任务 |

## 非目标（明确不做）

- 不把飞书文档当作可写回 Git 的双向权威编辑器（正文方向以 Git → 飞书为主；评论可反向导入）。
- 不托管多用户云端账号体系；每人在本机配置飞书自建应用。
- 不替代飞书权限体系本身——应用仍须被加为知识库成员或文件夹协作者。

- [需求-机器人协作](./需求-机器人协作.md)：播报、指令、权限分级、安静模式。
- [需求-评论回流](./需求-评论回流.md)：评论导入、增量更新、定时联动。
- [需求-工具箱](./需求-工具箱.md)：导出 Markdown、图表格式化。
